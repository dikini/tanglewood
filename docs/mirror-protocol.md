# Linux mirror protocol

SQLite remains the recovery source. Source mutations use App commands; filesystem workers never mutate ECS or SQL. Explicit import reads UTF-8 text on a worker and returns it for CreateNote/EditNote with a captured revision. Explicit export writes a selected snapshot without changing source. All managed paths are vault-relative Markdown paths; reject symlink ancestors and symlink leaf files.

## Durable store migration

Schema version 2 adds `export_baselines(note_id PRIMARY KEY, path UNIQUE, text)` and `pending_exports(note_id PRIMARY KEY, path, text, revision, trashed)`. Save a full note and upsert its pending export in the same SQLite transaction when mirror mode is enabled. Retain the baseline until export acknowledgement. On startup load pending exports and their baselines, then retry. Completion must contain note ID and revision; delete pending work only if its revision matches. An older successful export updates the physical baseline but never clears newer pending work. A failure retains pending work and surfaces its diagnostic independently from database save status.

Begin with one export in flight per note, coalescing only unsent full states. A filesystem job receives the durable note snapshot and baseline. Before replacing an existing target compare its exact UTF-8 bytes with the baseline. A file already equal to the desired text is an idempotent success, covering a crash after replacement but before acknowledgement. A different file with no matching baseline is a conflict; preserve both database text and external file for explicit resolution. Write a sibling temporary file, sync it, rename it into place, and sync the parent directory. A rename removes the old path only if its bytes still match its baseline; an externally changed old path blocks the export. Trash removes the mirrored path only when it matches the baseline and retains the note in SQLite. Missing files do not delete notes.

Rescan walks Markdown files without following symlinks. Known path with external text differing from baseline and accepted text equal to baseline is an external-only edit: issue revision-checked EditNote. Both changed means conflict; do not issue an edit or overwrite the file. Unknown files become CreateNote requests. A missing known path is a recoverable missing-file observation, never TrashNote. External renames appear as missing old path plus new import. After an imported change is durably saved, ordinary outbox export establishes its baseline.

The filesystem helpers enforce path and symlink checks immediately before I/O, but cannot exclude arbitrary external changes between comparison and rename. This milestone deliberately does not claim a fully race-free protocol with external editors. No watcher, hard deletion, automatic external rename detection, or background Android mirror is included.

## App integration contract

`App::open` remains database-only by default. A local-only `SetMirrorEnabled { enabled }` command persists a boolean setting before scheduling any mirror jobs. Linux startup may enable it explicitly with `--mirror`; disabling stops new exports but preserves pending records for a later resume. `ImportMarkdown { source_path, destination }`, `ExportMarkdown { id, path }`, and `RescanMirror` are local-only commands. Trusted local UI/CLI supplies filesystem roots; automation cannot select arbitrary filesystem paths. Commands return accepted I/O request IDs, and later results stay distinct from database save acknowledgements. An import job carries the captured target ID/revision (or create intent) so its completion cannot overwrite intervening edits.

Schema version 2 includes `mirror_conflicts(conflict_id INTEGER PRIMARY KEY, note_id, revision, path, database_text, external_text NULL, kind, note_path)` in the same migration. On an export/rescan conflict, send the observed external bytes and accepted snapshot to the storage worker; it commits the conflict record before App advertises a retained conflict. Preserve pending export and old baseline. External absence uses NULL, distinct from an empty file. A file error alone is not durable conflict retention. Repeated identical observations can be deduplicated, but never replace an older differing external version. Conflict recovery/resolution is explicit: recover either version as a note or revision-checked edit, then retry. Do not automatically clear pending work or delete externally changed paths after a conflict.

## Current application API

`execute` returns `CommandResult::Accepted { request_id }` for I/O commands. Poll `io_status(request_id)` while driving `tick`; `Completed` for import means the shared source command accepted the bytes, not that SQLite committed them. `flush` waits for accepted source saves; `flush_files` is a separate explicit blocking test/CLI boundary for pending file work. The GUI uses `tick` and `export_status(note_id)` and must keep export errors separate from `SaveState`. Import replacement requires `ImportDestination::Replace { id, expected }`; a concurrent edit makes the completion stale. Explicit import and export accept OS paths from trusted local callers, while Create destinations and mirror paths remain vault-relative. Mirror files live under `<vault>/markdown`.

Orderly `shutdown` flushes source changes, joins filesystem work, and closes storage. It may leave durable pending exports for restart; a file conflict does not prevent an acknowledged database save. Dropping an App also joins its filesystem worker before releasing the exclusive vault lock. No filesystem or SQLite I/O occurs inside note command execution.

Conflict history is exposed by `mirror_conflicts`; clients can recover its external text using ordinary revision-checked edit/create commands, then request `retry_saves` after explicitly resolving the file. History remains durable. Missing files are represented by a NULL external value and retain their source note. Automatic filesystem retries pause after an error and resume with `retry_saves` or on restart. Rename cycles can conservatively surface external conflicts; they never overwrite another mirrored note to force a rename through.

For an app rename cycle held by mirror ownership, first rename each participating note to a fresh unused path using ordinary revision-checked RenameNote commands. Call `retry_saves`, wait for database saves and exports to complete, then rename those notes to the final desired paths and save/export again. This releases the old physical paths without allowing one note's cleanup to delete another note's file. The integrated identical-content swap scenario exercises this recovery through the public App API. `mirror_conflicts` retains every database/external snapshot throughout; no manual SQLite modification is needed. Text equality permits idempotent retry only after App has checked path ownership against other accepted notes and their mirror baselines.
